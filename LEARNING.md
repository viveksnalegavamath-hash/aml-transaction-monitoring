# Learning log

Design decisions, what I learnt, and why.

## Setup

- PostgreSQL runs in Docker, bound to 127.0.0.1: same setup on my laptop and on AWS, and unreachable from the network.
- uv manages Python: one locked environment (uv.lock), no clash with Anaconda.
- dbt Core 1.x, because dbt v2 does not support PostgreSQL yet.
- Secrets live only in .env (git-ignored); gitleaks blocks any commit containing a secret.
- Raw data is git-ignored; the project uses synthetic and public data only.

## Phase 1 — Raw data loading

- **Raw layer, untouched.** CSVs load into schema `raw` exactly as downloaded, every column as text. Why: lineage and audit — any number can be traced back to the source file, and cleaning can be redone without re-downloading. Typing and cleaning happen in dbt staging, where they are tested. Alternative: typed columns at load time — rejected, because one malformed value would fail the whole load and hide what the source really contained.
- **PostgreSQL `COPY`, client-side (`COPY ... FROM STDIN`).** Python streams the file from the Mac to the database in Docker in 1 MB chunks. Why: COPY is the fastest bulk-load path (millions of rows in about a minute), and client-side streaming works even though the server cannot see files on my Mac. Alternatives: pandas `to_sql` (row inserts, far slower and memory-hungry); server-side `COPY FROM '/path'` (would need the file mounted into the container).
- **Empty-and-load in one transaction.** `TRUNCATE`, `COPY` and the log entry commit together or not at all. Why: a failed or interrupted load never leaves the table empty or half-loaded — the previous data stays. In PostgreSQL, `TRUNCATE` is transactional, so it rolls back too. Alternative: `DROP` + recreate — same safety, but loses grants and any comments on the table.
- **Header check before loading.** The loader compares the CSV header with the expected column list and stops with a clear error naming missing, unexpected or reordered columns. Why: if a source changes its layout, we fail loudly instead of loading values into the wrong columns.
- **Audit table `raw.load_log`.** One row per load: target table, file name, row count, loaded-at time. Why: banks must evidence what data entered the system and when; it also lets us reconcile row counts later in dbt tests.
- **Connect via 127.0.0.1, credentials from `.env`.** `localhost` reached a different PostgreSQL on this Mac.
- **IBM HI-Small: duplicate "Account" headers renamed by position.** The file has two columns both called `Account` (sender's, then receiver's). The header check still expects the file's exact 11 headers; only the table columns are named `from_account` / `to_account`. Why: a table cannot have two columns with the same name, and the position tells us which is which. Other headers become lower case with underscores (`From Bank` → `from_bank`). Alternative: edit the CSV header — rejected, raw files are never edited.
- **Bank IDs kept as text.** IDs like `010` would lose their leading zero as numbers, and `010` and `10` might then wrongly look like the same bank.
- **UK Sanctions List: preamble line skipped, but kept as evidence.** Line 1 is `Report Date: 02-Oct-2026`; the header is line 2. The loader skips it before COPY and stores it in `raw.load_log.source_note`. Why: a bank must be able to show which version of the list a customer was screened against; the daily re-screening (Phase 4) also depends on knowing the list date. Alternative: just drop the line — rejected, it is the only record of the list version.
- **Column names: any run of spaces or punctuation becomes one underscore.** `D.O.B` → `d_o_b`, `Nationality(/ies)` → `nationality_ies`. Why: names with dots, brackets or slashes need double quotes in every SQL query. Business-friendly names (`date_of_birth`) come in dbt staging. SAML-D and IBM names are unchanged by this rule.
- **The sanctions list is "flattened": many rows per designation.** Rows repeat for each name/alias and each address (and possibly other multi-value details), all sharing a `Unique ID`. 58,502 rows cover only 6,370 designations. Staging must de-duplicate to one row per designation plus a separate name/alias list before screening, or one person would produce dozens of matches.
- **Profile before cleaning.** Ten SQL queries in `sql/profiling/saml_d_profile.sql`, findings with numbers in `data/README.md`. Why: every cleaning step and rule threshold should rest on a measured fact. Answers "how do you know the data is clean?" Alternative: pandas profiling in a notebook — rejected, it would need the 9.5M rows in memory, and SQL in the repo can be re-run by anyone with one command.
- **Profiling findings that change the build:** ~~amounts are in the payment currency (4.3% non-GBP → FX conversion needed for `amount_gbp`)~~ (wrong — corrected in the dbt section below: amounts are treated as GBP); cross-border should be derived from the two countries, because 417 rows disagree with `payment_type`; "Dirham" (AED) and "Moroccan dirham" (MAD) are different currencies; typology names are inconsistent; structuring averages ~5,246, below R01's £8k–£10k band — to check in calibration.
- **Licences recorded from source metadata, not memory.** SAML-D is CC BY-NC-SA 4.0 (non-commercial, share-alike — fine for a portfolio project); IBM is CDLA-Sharing 1.0.
- **KYC customers = accounts that send money (292,715), not all 855,460 accounts.** A real bank holds KYC only on its own customers; accounts that only receive are outside counterparties. Checked first: the receiver is also a customer in 92.5% of suspicious transactions, so receiver-side rules (R02) still see almost all laundering accounts.
- **Synthetic KYC with no label leakage.** The generator's only input is the list of customer IDs; all attributes come from fixed distributions in `config/kyc_generator.yaml`. Why: if any attribute depended on the suspicious label, rules and models would look clever while reading the answer key. Also not derived from transaction behaviour — e.g. declared income from real inflows would make R10 circular. Enforced by tests (no mention of the label; exactly one read from the transactions). Proven by an evaluation query: KYC distributions are the same for suspicious-linked and other customers. Alternative rejected: planting realistic correlations (e.g. more PEPs among launderers) — that is leakage by design.
- **Consequence stated honestly:** KYC carries no real laundering signal in SAML-D, so KYC-based features will add little detection power. The value shown is the risk-rating process.
- **Reproducible generation.** IDs sorted, NumPy and Faker seeded (20261014), every attribute drawn for every row in a fixed order, Faker version pinned. Two full runs → identical MD5 fingerprint.
- **Settings in YAML, not code** (`config/`): shares, distributions and occupation lists are readable assumptions, like rule thresholds. Income depends on occupation only (a student does not declare £80,000) — still independent of transactions.
- **KYC risk rating not generated.** It is the bank's judgement, so it is computed later in dbt from the facts + country risk, under documented rules.
- **Typed columns for generated data.** Raw downloaded files stay text (to preserve the source exactly); the KYC table is created by us, so it gets real types plus a CHECK that `is_synthetic` is always true.
- **Dataset artefact:** "receiver is also a customer" is true for 92.5% of suspicious vs 33.2% of normal transactions — a side effect of how SAML-D generates typologies, not real-world behaviour. Handle such features with care in Phase 3.
- **COPY names its columns.** `COPY raw.t (col1, col2, ...)` instead of relying on column order, so if a table built earlier has different columns, the load fails loudly instead of putting values in the wrong place.

## Phase 1 — Country risk (`ref.country_risk`)

- **Two views of country risk, in separate columns.** `fatf_status` / `fatf_measure` (the FATF's official lists) and `internal_rating` (our own judgement from World Bank data). Why: they answer different questions. FATF says "this country has an agreed action plan or is subject to countermeasures"; the internal rating says "governance here is weak". They disagree on purpose — Monaco is grey-listed but rates low risk (Kuwait, Bulgaria and Vietnam medium); Pakistan, Nigeria, Mexico and Turkey are not listed but rate high. Merging them into one score now would hide that; the combined score is a documented policy step later in dbt. Alternative: a single blended number — rejected, an analyst could not see why a country is high risk.
- **FATF lists parsed from saved pages, never typed in.** The FATF site blocks automated downloads (HTTP 403), so the pages are saved from the browser into `data/raw/fatf/` and parsed with Python's built-in HTML parser. Jurisdictions, measure, list date (from the page title) and source URL (the page's own canonical link) all come from the file. Why: a list typed from memory is unauditable and goes stale silently. Alternative: copy the list into YAML — rejected for the same reason.
- **The measure comes from the section heading above each country.** On the call-for-action page, DPRK and Iran sit under "apply countermeasures", Myanmar under "apply enhanced due diligence". On the grey-list page, countries under "No longer subject to increased monitoring" (Algeria, Namibia — June 2026) are recorded as removed and never loaded. Why: the page structure is the evidence. The parser reads the headings, not the summary "Country" box, because that box has a typo (missing comma: "Papua New Guinea South Sudan").
- **Strict parsing: unknown headings stop the build.** Every heading must be a known section, a known non-country heading (listed in the YAML), or a country with an ISO code. Why: if the FATF changes the page layout, we want an error, not a silently shorter list. Also checked: the page title matches the expected list (catches swapped files), one date for both lists, no country on two lists, no country both listed and removed.
- **Internal rating: WGI, three indicators, averaged, split into thirds.** Control of Corruption, Rule of Law and Regulatory Quality (decided 21 Oct 2026) — the three most tied to money-laundering risk (corruption proceeds, enforcement, quality of financial regulation). The other three (voice and accountability, political stability, government effectiveness) are more about politics. Countries are ranked by the average, weakest first, and split into equal thirds: 71 high, 71 medium, 71 low. Ties broken by ISO code, so the result never depends on row order. Alternatives: fixed cut-offs (e.g. average < −0.5 = high) — rejected for now because the numbers would be arbitrary; Basel AML Index — not open-licensed. Thirds are a relative measure: a country can move band when others improve. Stated as a limitation.
- **WGI from the World Bank API, saved to disk first.** `ingestion.wgi` saves the API's JSON unchanged into `data/raw/wgi/`; the build reads the saved files. Why: same lineage idea as the raw CSVs — what we rated can always be traced to an exact file and release (`lastupdated` 2026-09-25, data year 2025). Licence CC BY 4.0. Checked on read: right source, one page only, right indicator and year, all three files from the same release.
- **A country needs all three indicators to be rated.** French Polynesia and New Caledonia lack Regulatory Quality; Virgin Islands (UK) has no WGI data at all. They get a row with `internal_rating` empty, not an invented value. Why: a guessed rating would look like evidence. Alternative: treat "unrated" as high (a common bank policy) — that is a policy choice, so it belongs in the dbt combination step, not in the raw rating.
- **Names to ISO codes in YAML, matched loosely.** `config/country_risk.yaml` maps SAML-D names (`UK`, `UAE`) and FATF spellings (`Lao PDR`, `Côte d'Ivoire`) to ISO 3166 codes. Matching ignores case, extra spaces and curly vs straight apostrophes, because the FATF page writes "nEPAL" and "BOsnia and Herzegovina". Codes are quoted in YAML: unquoted `NO` (Norway) becomes the boolean false. Every code was cross-checked against the World Bank's own country name for that code.
- **WGI rows without a code must be mapped or skipped on purpose.** Eight economies come without a code: seven mapped by name (Jersey, Taiwan, ...), "Netherlands Antilles" (dissolved 2010) explicitly skipped. Any new one stops the build. This caught Taiwan on the first run.
- **Hard stop, with rollback.** If any SAML-D location, KYC nationality or FATF jurisdiction has no row — or a SAML-D / KYC country has no internal rating — the load raises an error listing every gap, inside the same transaction, so nothing is saved. Proven on the real database by deleting "Turkey" from the settings: the run stopped and the tables kept their previous rows. Why: a transaction from an unknown country silently scored as "no risk" is exactly the gap a regulator would criticise. The FATF check reads the pages again rather than trusting the built rows, so it is independent.
- **Date and source on every row.** `fatf_list_date`, `fatf_source` (the page that lists the country; both pages for a country on neither — absence is proven by both), `wgi_version`, `wgi_data_year`, `wgi_source`. Why: anyone looking at one row can tell which list version it reflects, without a join. Needed for the refresh after the FATF plenary (26–30 Oct 2026).
- **Built in Python into schema `ref`, not in dbt (yet).** It parses HTML and JSON, which dbt cannot do; dbt is not set up yet. `marts.dim_country` will read `ref.country_risk`. Generated tables get real types and CHECK constraints (e.g. not listed ⇔ no measure), like the KYC table.
- **No new dependencies (country risk).** HTML parsing with the standard library's `html.parser`, downloads with `urllib` — nothing to add to `pyproject.toml`.

## Phase 1 — dbt project

- **dbt Core 1.12.5 + dbt-postgres 1.11.0, pinned exactly, as a separate uv tool.** `uv tool install --force "dbt-core==1.12.5" --with "dbt-postgres==1.11.0"`. Why: dbt v2 does not support PostgreSQL, and an unpinned `uv tool upgrade` could jump to it. Kept outside the project environment because dbt's own dependencies can clash with MLflow's. Alternative: a uv dependency group in `pyproject.toml` (locked in `uv.lock`) — rejected for the clash risk; the exact pins are recorded here instead.
- **`profiles.yml` committed, with no secrets.** Every credential is `env_var('POSTGRES_...')`. dbt 1.12 loads `.env` by itself, searching upward from the folder it runs in, so plain `dbt build` inside `dbt/` works. Proven: run from a folder with no `.env` above it, dbt stops with "Env var required but not provided". Alternative: `~/.dbt/profiles.yml` outside the repo — rejected, the connection settings would then be invisible to anyone reading the project.
- **Exact schema names.** A `generate_schema_name` macro writes models to `staging`, `marts` and `evaluation` as named, instead of dbt's default `dbt_dev_staging`. Why: readable schemas, and the `evaluation` schema (labels only) can be locked away from the read-only role later.
- *(Superseded the same day — HMRC rates are loaded but not applied to SAML-D; see "Correction" below.)* **FX source for `amount_gbp`: HMRC monthly exchange rates** (GOV.UK Trade Tariff), chosen 22 Oct 2026. Why: the only single source covering all 12 non-GBP currencies in SAML-D (including PKR, NGN, MAD, AED, MXN, ALL), already quoted as units per £1, and a UK government source. Licence: Open Government Licence v3.0 — confirmed by Vivek on 22 Oct 2026 from the Trade Tariff exchange rates page footer ("All content is available under the Open Government Licence v3.0, except where otherwise stated"). Alternatives: Bank of England daily spot rates and ECB reference rates — rejected, each misses five or six of our currencies, so a second source would be needed.
- *(Applies only if rates are used, e.g. for IBM later.)* **Known limitation: one rate per currency per month** (HMRC takes it at midday on the day before publication). Every transaction in a month is converted at that single rate, so `amount_gbp` can differ from the day's real rate, especially for volatile currencies (TRY, NGN, PKR moved a lot in 2022–23). Acceptable for AML monitoring: thresholds are approximate and 95.7% of rows are paid in GBP anyway. Stated in `data/README.md`.
- **Country names mapped in one place only.** The country-risk loader writes `ref.country_name_map` (43 names → ISO code) straight from `config/country_risk.yaml`, in the same transaction as `ref.country_risk`; dbt staging joins SAML-D's location names to it. Why: a dbt seed with the same mapping would be a second copy that can drift from the YAML. A foreign key to `ref.country_risk` means the database itself rejects a mapped code with no country-risk row. `name_key` is the name in lower case, single spaces, straight apostrophes; dbt applies the same rule in SQL (all 18 SAML-D locations checked to match).
- **dbt usage statistics off.** `send_anonymous_usage_stats: false` in `dbt_project.yml`, and `dbt/.user.yml` (dbt's random per-user ID) git-ignored. Why: nothing about this project leaves the machine unless we choose to send it; set in the project, so it applies to anyone who runs it.
- **Staging = views, with no label anywhere.** `stg_saml_d` never selects `Is_laundering` or `Laundering_type`, and the typology name-cleaning seed waits for the evaluation model (step 5) rather than sitting in staging. Why: anything a rule or feature can `select` from, it might one day select by accident. Checked: no column in `staging.stg_saml_d` contains "launder".
- **Transaction ID = MD5 of every non-label column** (macro `saml_d_transaction_id`). SAML-D has no ID; the non-label columns were checked unique on all 9.5M rows first. One macro used by staging and evaluation, so both compute the same ID. Alternative: `row_number()` — rejected, it changes if row order changes, so labels could be joined to the wrong transaction.
- **Left joins to lookups, then `not_null` tests.** An unmapped currency or country becomes NULL and fails a test, instead of an inner join silently dropping the row. The row-count reconciliation catches dropped rows too.
- **Two small home-made tests, no dbt packages.** `row_count_matches_load_log` (model rows = latest `raw.load_log` count; also fails if the table was never logged) and `is_positive`. Why: dbt_utils would add a dependency for two ten-line tests. The reconciliation test was proven to fail: pointed at the wrong log entry it returned both counts (9,504,852 vs 292,715).
- **Staging reproduces the profiling numbers:** 417 rows where `payment_type` disagrees with the countries, 934,348 cross-border rows (9.83%). `dbt build --select staging` — 1 seed, 4 views, 40 tests — passes in about 2 minutes; most of that is tests recomputing the view over 9.5M rows, which is fine for views and is why marts will be tables.
- **Correction: SAML-D's `Amount` is treated as GBP for every currency; no FX conversion** (decided by Vivek, 22 Oct 2026). Profiling had *assumed* amounts were in the payment currency. Building `amount_gbp` with HMRC rates and hand-checking one naira row (2,255.79 NGN → £3.93) looked wrong, so I compared medians by currency: ~7,100–7,650 in every currency, 1.18–1.27× the GBP median, whatever the exchange rate (JPY 168 per £1, NGN 616). Real local-currency amounts would differ by those factors. Converting would have made a typical naira payment £13 and broken every amount-based rule for 4.3% of rows. Alternatives: convert anyway (follows the column labels literally, wrong scale); keep both columns (adds a column nobody should use). Guarded by dbt test `saml_d_amounts_on_common_scale` (fails if any currency's median leaves 0.5–2× the GBP median). HMRC rates stay loaded and tested for IBM HI-Small. **Lesson: test an assumption about units against the data before building on it — a single hand-checked row caught this.** Interview story: a plausible profiling note was wrong, and a sanity check on the output caught it before any rule used it.
- **Marts as tables, with indexes.** `fct_transactions` (9.5M rows, ~2¾ min to build) has indexes on `transaction_id` (unique), `sender_account`, `receiver_account` and `transaction_ts` — the columns rules will filter and window on (`receiver_account` added for receiver-side rules such as R02). *(Changed in Phase 2 step 3: the account indexes became `(account, transaction_ts)` composites.)* `dim_country`, `dim_customer` are small tables.
- **Labels in their own schema.** `evaluation.eval_transaction_labels` (transaction ID, `is_laundering`, standardised typology) and its typology seed live in schema `evaluation`, so the read-only role for the API and dashboard can simply be denied it. The ID comes from the same macro as staging; a relationships test proves every label row matches a transaction. A singular test checks every label agrees with its typology's suspicious flag (the seed's flags were typed from profiling, so they are verified against the data). A pytest test fails if any staging or mart model mentions the label.
- **`sender_is_customer` always true, by design** (customers = sending accounts), asserted by a test so a future change to the KYC rule is noticed. `receiver_is_customer` reproduces the dataset artefact exactly (92.5% of suspicious vs 33.2% of normal) — documented on the column.
- **No combined country score or customer risk rating yet.** `dim_country` keeps FATF and internal rating separate; `dim_customer` carries the nationality's two views. Combining them is policy, for Phase 2 scoring.

## Phase 1 — Dev sample

- **10% account sample (≈19% of rows), chosen by hashing the account ID.** `int(md5(account_id)[:8], 16) % 100 < 10`, as a dbt macro (`in_dev_sample`) and identical in Python. Why accounts, not transactions: AML rules and features look at an account's history (90-day windows, velocity, fan-in/fan-out); a random 10% of transactions would leave every account with gaps. Why a hash: deterministic and reproducible on any machine, with no seed to manage, and it never sees the label. md5 rather than PostgreSQL's `hashtext()`, which is internal and may change between versions. Alternative: 5% of accounts (~10% of rows) — rejected by Vivek: twice the suspicious cases (1,791 vs 921) makes dev metrics less noisy.
- **Keep a transaction if the sender OR the receiver is sampled, full date range.** Sampled accounts then have complete histories in both directions. Consequence: 10% of accounts → 19% of rows (~1 − 0.9²), so it is always labelled "10% account sample (≈19% of rows)" to avoid confusion with 10% of transactions. Caveat: counterparties outside the sample have partial histories — judge rules and features on sampled accounts only.
- **Off by default, separate schemas.** `dev_sample: false` in `dbt_project.yml`, so a plain `dbt build` always uses all 9.5M rows (a pytest test checks the default). The sample builds into `*_sample` schemas, so it can never overwrite the full tables. The reconciliation test compares against raw filtered by the same rule, so it still catches lost rows instead of being switched off.
- **The sample is representative on what we can check:** suspicious rate 0.099% vs 0.104%, all 28 typologies, full date range (evaluation-only query; the label describes the sample, never chooses it).
- **All reported results come from the full data** — now project rule 10 in CLAUDE.md. Why: the sample is a development convenience; a number quoted on a CV or in model documentation must be reproducible on the whole dataset.
- **`stg_saml_d` is a table in sample mode only** (Vivek's decision). First result: sample build ~3¼ min vs full ~6¼ min — less gain than estimated, because every test on the `stg_saml_d` view re-scanned and re-hashed all 9.5M raw rows. Fix: `config(materialized='table' if var('dev_sample') else 'view')`. Sample build now 78 s (~4.8× faster than full). In a normal build it stays a view — confirmed in `information_schema` (`staging.stg_saml_d` = VIEW, `staging_sample.stg_saml_d` = BASE TABLE). Lesson: in dbt, a view is re-computed by every test that reads it; materialise what many tests read.

## Phase 2 — Rules engine: decisions (22 Oct 2026)

- **Rule logic in SQL files, parameters in YAML.** `rules/<ID>_<name>.yaml` holds the spec and every threshold; `src/aml_transaction_monitoring/rules/sql/<ID>.sql` holds the logic with named placeholders (`%(min_amount_gbp)s`). Every value is bound by psycopg as a query parameter, never pasted into SQL text with string formatting — so a YAML typo cannot change or inject SQL. The engine checks every placeholder has a YAML parameter and every parameter is used. Alternative: SQL inline in YAML — rejected, harder to read, lint and test.
- **Time split for tuning: tune on 7 Oct 2022 – 31 May 2023; hold out 1 Jun – 23 Aug 2023 as the headline.** Why: thresholds tuned on the same labels that are reported would flatter the results. Rules may look back into earlier months for history (e.g. a 90-day average); the **alert date** decides which period an alert belongs to. The same hold-out is Phase 3's ML test period, so rules and ML compare like for like. Alternative: tune and report on all months — rejected as optimistic.
- **R05 extended for SAML-D.** As written (FATF call-for-action, or grey list ≥ £5,000) it can never fire: none of SAML-D's 18 countries is FATF-listed. FATF clauses kept (correct policy, matters for other data); added "≥ £5,000 to or from a country with internal rating high". Recorded in R05's change log.
- **R08 fallback.** Round-tripping within 4 hops is graph search; if recursive SQL is too slow on 9.5M rows, R08 moves to the Phase 3 network work (NetworkX) instead of consuming Phase 2 time.

## Phase 2 — Step 1: engine + R01 end to end

- **Rule SQL contract.** Every rule's SQL reads the transactions table through one placeholder (filled in by the engine as a quoted identifier: `marts` or `marts_sample`), takes each threshold as a named placeholder bound by psycopg, and returns the same five columns: `account_id, trigger_ts, window_start, transaction_ids, metrics`. The engine checks the column names, so every rule plugs in the same way. Gotcha found while building: psycopg reads placeholder syntax even inside SQL comments, so comments must not contain it.
- **Alert = one account, one rule, one trigger**, with a plain-English reason built from the YAML template and the alert's own numbers ("3 cash deposits of £8,000–£9,999.99 within 7 days, totalling £27,300.00"). Why: an analyst must see *why* without reading SQL. `alert_transactions` links each alert to the transactions behind it — that is how evaluation later decides whether an alert caught suspicious activity.
- **Suppression in Python, not SQL.** Rolling windows produce a candidate for every qualifying transaction; the engine keeps the first per account, then none within `suppression_days` (YAML). Simple, testable, and identical for every rule. Trade-off: transactions arriving during the suppression period are not linked to any alert — stated, and visible in the evaluation.
- **Deterministic alert IDs** (md5 of rule, account, trigger time) and a full replace of a rule's alerts on each run, inside one transaction with a `rule_runs` audit row (dataset, rule versions, candidate and alert counts). Re-running gives the same alerts, never duplicates. Analyst status changes (Phase 4) will need a different policy than full replace.
- **Three guards keep labels out of rules:** the engine refuses SQL mentioning `evaluation`, `laundering` or typologies (even in comments); pytest scans every rule SQL file; and the rules only ever receive `fct_transactions`, which has no label. A database role without access to `evaluation` follows in Phase 4.
- **Rule tests run real SQL on a throwaway schema.** A pytest fixture creates `test_rules_<random>` with a tiny `fct_transactions`, inserts hand-made rows, runs the rule, and drops the schema (checked: none left behind). Why real PostgreSQL: the logic *is* SQL (window frames, intervals); a Python imitation would test the imitation. Skipped automatically if the database is down.
- **Finding: R01 at its textbook values never fires on SAML-D.** Only 45 of 9.5M transactions are cash deposits of £8,000–£9,999.99, and no account gets three within 7 days — 0 alerts on the full data. Consistent with profiling (structuring averages £5,246). Not changed now: tuning (step 7) decides, on the tuning months only. The engine's write path is proven by the end-to-end test instead.

## Phase 2 — Step 2: R02 and the evaluation report

- **R02 Many-to-one with a lateral look-back.** PostgreSQL cannot `count(distinct …)` over a sliding window, so for each incoming payment a lateral subquery looks back over that account's inflows in the window (using the index on `receiver_account`). Only accounts that *ever* had 10+ distinct senders are examined — a cheap pre-filter that keeps the lateral affordable. On the dev sample: 179,379 candidates → 1,643 alerts after 7-day suppression, ~25 s.
- **Evaluation joins labels to alerts that already exist — never the other way.** `evaluation/rules_report.py` is the only Python allowed to read `eval_transaction_labels`; a pytest test scans every other module for it (and was checked to detect the evaluation code itself, so it is not vacuous).
- **Metric definitions.** Precision = share of alerts covering at least one suspicious transaction (via `alert_transactions`). Recall = share of suspicious transactions covered by at least one alert. Alerts per week = analyst workload. Rule × typology matrix = share of each typology's suspicious transactions each rule catches, plus "any rule" (no alert count or precision for "any rule": alerts overlap across rules). Never accuracy. Alerts belong to the period of their alert date; suspicious transactions to the period of their transaction date. Edge effect, stated: a June alert can link to late-May transactions through its look-back window.
- **Rules with no alerts still appear (0 alerts, 0% recall).** The rule list comes from `rule_runs`, not from the alerts — otherwise a silent rule like R01 would vanish from the report and look like it was never run.
- **Reproducible numbers:** the report header lists each rule's version and run ID; periods come from `config/evaluation.yaml`, shared with Phase 3.
- **Sample reports are printed, never saved.** `--sample` logs the report marked "DEV SAMPLE - not for reporting"; only a full-data run writes `docs/results/rules_evaluation.md` and `.csv`. This enforces CLAUDE.md rule 10 in code, not just in docs.
- **First look (dev sample, not for reporting):** R02 precision is very low (~0.5%) — SAML-D has millions of *normal* fan-in transactions (`normal_fan_in`, `normal_small_fan_out`), so "many senders" alone is not distinctive. Expected for a textbook threshold; tuning and the full-data baseline will quantify it.

## Phase 2 — Step 3: R03 and R04

- **R03 One-to-many = R02 mirrored** (sending account, distinct receivers, same lateral look-back). Plan's starting values kept: 10 receivers in 7 days, **no minimum total**. Alternative: copy R02's £20,000 floor — not done, because the plan did not specify one and adding it now would be tuning without evidence. Tuning (step 7) decides, on the tuning months only.
- **R04 Rapid pass-through: money must come in before it goes out.** The trigger is an outgoing payment. Inflows are counted over the last 48 hours, but outflows only from the first of those inflows onwards. Why: with plain 48-hour totals, "paid £9,000 out on Monday morning, received £10,000 an hour later" would look like pass-through. A test proves this case does not fire. The ratio can exceed 100% (the account may already have had a balance); that still counts as pass-through.
- **R04 in two stages for speed.** Stage 1: one sorted pass over every account's money in and out with rolling 48-hour sums, which keeps only triggers that *could* qualify. Stage 2: an exact re-check for those few, with the "in before out" condition. Stage 1 can only let through too many candidates, never too few (its outflow total includes everything stage 2 counts), so the result equals the exact rule. On the sample: 23,617 candidates → 4,588 alerts in ~13 s.
- **Performance fix: composite indexes `(account, transaction_ts)`.** R03's first sample run did not finish in 10 minutes (stopped). Cause: the index was on `sender_account` only, so each look-back read *all* of the account's payments and then discarded those outside the 7 days. The cost grows with the square of an account's payment count: ≈275M row reads on the sample, against ≈60M for R02. `fct_transactions` now has indexes on `(sender_account, transaction_ts)` and `(receiver_account, transaction_ts)` in place of the single-column ones. A composite index still serves lookups on the account alone, so nothing loses out. R03: >10 min → 35 s; all four rules on the sample in ~1½ min. Rebuilt in both sample and full schemas (dbt 17/17 each). Lesson: for "per account, within a time window" queries, index the account *and* the time together. Interview point: reading the problem as a query-cost question (row reads per trigger) rather than guessing.
- **First look (dev sample, not for reporting):** the hold-out shows R03 at ~173 alerts/week, 0.5% precision, 3.1% recall, and R04 at ~113 alerts/week, 1.1% precision, 5.1% recall. R04 catches most `cycle` cases (money comes back through the account) but none of the scatter-gather / gather-scatter it was aimed at — to investigate in tuning (amount or timing likely outside £10,000 / 48 h). Too many alerts for too little recall at textbook values; quantified on full data in step 6.
- **Kept as built for the baseline** (Vivek, 22 Oct 2026). R03 and R04 run at their plan values in step 6, so the baseline shows the untuned rules.
- **Notes for step 7 (tuning, tuning months only):**
  1. **Tune R03 too**, not only R01/R02/R06: it has the highest alert volume of the four rules. Consider adding a minimum total (like R02's £20,000) and record it in the change log if adopted.
  2. **Find out why R04 misses scatter-gather.** Test the two explanations separately: (a) each mule account receives under £10,000, so the inflow threshold is never reached, or (b) the money takes longer than 48 hours to leave. Look at the amounts received and the in-to-out delays for the scatter-gather accounts, then decide which parameter to change, if any.

## Phase 2 — Step 4: R05, R06 and R07

- **R05 High-risk jurisdiction is per payment and checks both sides.** The plan's FATF clauses are kept as written and look only at money *sent*: any payment to a call-for-action country, or ≥ £5,000 to a grey-list country, alerts the sender. The new clause, ≥ £5,000 *to or from* a country with internal rating high, alerts the sender for money going out and the receiver for money coming in. Recorded in R05's change log. One alert row lists every clause the payment matched ("FATF increased monitoring; internal rating high"). On SAML-D only the new clause can fire, because no SAML-D country is FATF-listed (Pakistan, Mexico, Nigeria and Turkey are rated high). Alternative: FATF clauses on both directions too — not done, because the plan wrote "to", and inbound grey-list money is covered by the internal rating where it matters.
- **History = the account's first transaction in the data, sent or received** (R06 and R07, `min_history_days: 90` in YAML). Neither rule fires until an account has 90 days of history, because before that there is no profile to compare with. The synthetic KYC onboarding date is deliberately not used: it is generated, not observed, and customers are senders only, so receivers would have no date at all. Consequence, stated: the data starts on 7 Oct 2022, so R06 and R07 cannot alert before 5 Jan 2023 (R07 spikes not before 4 Feb 2023). Their tuning period is therefore about 5 months instead of 8. An account active before the data starts looks new at first — the usual "cold start" of a monitoring system that goes live.
- **R06 Large vs profile.** A payment *sent* of more than £10,000 and more than 3× the account's average payment sent in the previous 90 days. The payment is excluded from its own average (`exclude group` in the window frame — a test proves £12,001 against a £4,000 average fires, which it would not if the payment diluted its own baseline). It needs at least one payment in the 90-day baseline (`min_baseline_payments: 1`, YAML): an account with older history but nothing in the last 90 days has no average to compare with. Alternative: compare against payments received too — not done, because "a large payment for this customer" is about what they send.
- **R06 uses the mean, as the plan says; a median may suit better — to test in step 7.** Transaction amounts are heavy-tailed: one large past payment pulls the mean up and hides the next one, while many tiny payments pull it down and make ordinary payments look "large". The median is robust to both. Cost: PostgreSQL has no median over a sliding window (`percentile_cont` is not a window function), so it needs a lateral look-back like R02 — slower. Test on the tuning months: mean vs median, compare precision, recall and alerts per week.
- **R07 Behaviour change looks at all activity, money in and out**, with two clauses:
  1. **Spike:** 30-day volume more than 5× the average 30-day volume of the 90 days *before* those 30 days. The baseline must not overlap the recent window: with an overlapping baseline, a spike would raise its own average and could never be 5× above it (30 days of volume V against a 90-day average of at least V/3). For the spike clause, the whole baseline period must lie inside the account's history (first transaction at least 120 days before), otherwise a partly empty baseline makes the account look quieter than it was. A zero baseline is not a spike (5× nothing is meaningless); that case is the dormancy clause's job.
  2. **Dormant:** the first transaction after at least 90 days with none. The account's first-ever transaction has no previous one, so it is *new*, not dormant — a test proves a new account's first large payments do not fire.
  - Volume counts money sent and received. Alternative: money sent only (like R06) — to compare in step 7.
- **Making sure tests are not vacuous.** Each history guard was briefly removed, and the test that should catch it was checked to fail. The R07 test first passed for the wrong reason (the account's first payment fell inside the baseline and raised the bar), so it was strengthened until removing the guard made it fail. Lesson: a passing "does not fire" test proves nothing unless it would fail without the condition it is about.
- **Speed (dev sample):** R05 ~1 s, R06 ~15 s, R07 ~1 min (371,757 candidates → 84,313 alerts) plus ~30 s writing alerts. R07 looks up the transactions behind an alert only for spike candidates (the look-up is skipped for reactivations).
- **First look (dev sample, not for reporting), hold-out:** R05 ~143 alerts/week, 1.0% precision, 3.5% recall; R06 ~699/week, 0.3%, 5.1%; R07 ~3,222/week, 0.7%, 47.4%. R07's recall is flattered: a spike alert links every transaction in its 30-day window, so it "covers" a lot. Notably, R07 catches **0%** of `behavioural_change_1` and `_2`, the typologies it was aimed at — R03 catches more of them.
- **The dev sample distorts history-based rules.** The sample keeps every transaction of a sampled account, but accounts outside the sample appear only through their transactions with sampled accounts, so their history is incomplete: they look new, dormant or spiky when they are not. 58% of R07's sample alerts (45% of R06's) are on non-sampled accounts. The full data has no such gap. One more reason why results come from the full data only (CLAUDE.md rule 10).
- **Notes for step 7 (tuning, tuning months only):**
  1. **R06: mean vs median** baseline (above).
  2. **R07 needs a minimum volume.** Example alert: "£276.93 in 2 transactions, 9.3 times the previous average of £29.88" — a big ratio on tiny money. Consider a floor like R02's (e.g. 30-day volume ≥ £10,000) and a minimum amount for reactivations.
  3. **R07: find out why it misses `behavioural_change_1/2`.** Look at those accounts' volumes and gaps, and test volume sent only vs sent + received.
  4. **R05: decide if £5,000 is right for the internal-rating clause**, and whether 7-day suppression is right for a per-payment rule (later payments to the same country within 7 days are not linked to an alert).

## Phase 2 — Evaluation fixes before the baseline (22 Oct 2026)

Two problems found in the step 4 sample results, fixed before the step 6 baseline (Vivek approved all four choices below).

- **1. Sample mode counts only sampled accounts.** New dbt model `marts.dim_account`: one row per account (sender or receiver), first and last transaction, and `in_dev_sample` from the *same* macro as the sample filter, so the sampling rule exists once. The report with `--sample` keeps only accounts with `in_dev_sample` true: their alerts, their suspicious accounts, and suspicious transactions with at least one sampled party, caught only through a sampled party. The full-data report is unaffected (every account counts). The rules themselves are not filtered: the engine behaves the same on sample and full data. Alternative: copy the md5 expression into the report SQL — rejected, two copies of one rule can drift apart. dbt test: about 10% of accounts flagged in a full build (9.97% of 855,460). Gotcha: that test first did not run in sample builds, because its `ref()` sat inside a Jinja `if` that was false, so dbt did not see the link. Lesson: dbt finds dependencies by rendering the SQL, so `ref()` must not be hidden behind a condition.
- **2. One scoring rule for every rule, independent of what a rule links.** Before, recall counted the transactions each rule linked to its alerts. R07 linked its whole 30-day window and got credit for transactions it never examined, while R05/R06 linked a single payment, so the numbers were not comparable (precision had the same problem). Now `alert_transactions` is evidence for analysts only, not used for scoring. A **suspicious account** is the sender *or* receiver of a suspicious transaction: rules alert both sides (R02 receivers, R06 senders), and in the full hold-out the 2,837 suspicious transactions involve 1,499 senders and 1,298 receivers (2,490 accounts, 307 in both roles). `detection_days: 30` (config/evaluation.yaml) is the same window for every rule, the longest look-back of any rule (R07):
  - **Account recall (headline):** share of suspicious accounts with an alert from the rule in the same period. It credits an alert raised for an unrelated reason on a suspicious account — deliberately: an analyst reviews the whole account.
  - **Transaction recall:** a suspicious transaction is caught when the rule alerted its sender or receiver at the time or up to 30 days after. An alert raised *before* a transaction does not catch it.
  - **Precision:** share of alerts whose account had a suspicious transaction (sent or received) in the 30 days up to the alert — the mirror image of transaction recall.
  - Alternatives considered: keep linked-transaction recall as an extra column (invites the comparison we removed); have each rule link only its "evidence" (still rule-specific); credit only the trigger transaction (too harsh on window rules like R02).
- **Base rate and lift (Vivek's addition).** Base rate = share of active accounts (any transaction in the period, either side) that are suspicious: what picking accounts at random would achieve. Lift = precision ÷ base rate, so a precision of 2% reads as "4× better than random" rather than just "low". Caveat, stated in the report: precision looks 30 days back, the base rate looks at the whole period, so a random account is more likely to count as suspicious under the base rate. That makes the base rate slightly high and the lift slightly understated — the conservative direction. Interview point: always read precision against the base rate; at a 0.5% base rate, 3% precision is a 6× improvement.
- **What changed in the sample numbers (hold-out, sampled accounts, not for reporting):** base rate 0.53% (255 of 48,380 active accounts). R07 transaction recall fell from 47.4% (old definition) to 25.8%, and its lift is 1.3× (0.8× in the tuning months — *worse than random*). R06 is now the strongest single rule: lift 5.4×, account recall 53%. R02–R05 have lifts of 3.5–5.5×. Any rule: 72% of suspicious accounts. R07 still catches 0% of `behavioural_change_1`; no rule does. Numbers from steps 2–4 are not comparable with these (different definitions).
